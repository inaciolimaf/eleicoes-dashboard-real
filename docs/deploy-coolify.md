# Deploy on Coolify

How to run the system on a Coolify server against the official TSE. The deploy uses
`docker-compose.coolify.yml` (build pack **Docker Compose**). That file is complete: it sets every
variable, and Coolify generates the secrets itself (`SERVICE_PASSWORD_*`), so **no variable has to
be typed in the panel**. For the differences from the local compose, see the table at the end; for
what the code does with each variable, see [`docs/system/overview.md`](system/overview.md).

## Variables

Coolify generates these four when the resource is created. They appear in the **Environment
Variables** tab; do not edit them by hand.

| Variable | Generated by Coolify | Used by |
|---|---|---|
| `SERVICE_PASSWORD_POSTGRES` | a password | `db` (`POSTGRES_PASSWORD`), and `DATABASE_URL` in the backend services |
| `SERVICE_PASSWORD_64_JWT` | a 64-character secret | `JWT_SECRET` (login tokens) in the backend services |
| `SERVICE_URL_WEB` | the public URL of `web` | `CORS_ORIGINS` in the backend services |
| `SERVICE_FQDN_WEB_80` | the generated domain of `web`, port 80 | the domain binding of `web` (Coolify's proxy) |

The rest of the configuration is fixed in the file (the values below come from the compose, not
from the panel):

| Variable | Value on Coolify | Meaning |
|---|---|---|
| `TSE_AMBIENTE` | `oficial` | the official TSE site |
| `TSE_BASE_URL` | `https://resultados.tse.jus.br/oficial` | base of the official dissemination files |
| `TSE_MAX_RPS` | `90` | the TSE blocks the IP for 10 minutes above 100 requests per second |
| `TSE_CONCORRENCIA` | `24` | concurrent requests to the TSE |
| `TSE_VERIFICAR_JWS` | `true` | the signature of the files is checked |
| `COLETAR_SECOES` | `true` | polling sections are collected |
| `MODO_SECOES` | `sob_demanda` | only the sections opened in a dashboard or watched by an alert (not `todas`, which takes hours) |
| `COLETAR_ZONAS` | `false` | electoral zones are not collected (they multiply the volume and stalled the worker) |
| `FILA_MAX` | `3000` | the collector stops downloading municipalities above this queue size |
| `INTERVALO_CATALOGO` / `_PRINCIPAL` / `_ACOMPANHAMENTO` / `_MIN_MUNICIPIO` | `30` / `5` / `5` / `20` | seconds between collection cycles |
| `LOCAIS_VOTACAO_URL` | the TSE open-data ZIP of polling places (2026) | polling places (locais de votação) |
| `WORKER_CONCORRENCIA` | `6` | consumers in each worker process |
| `LOG_LEVEL` | `INFO` | log level |
| `ENVIRONMENT` | `production` | the production checks run (a short or example `JWT_SECRET` stops the process), and the logs are JSON lines (see Notes) |
| `MIGRAR_AO_SUBIR` | `"true"` (on `api` only) | `api` runs `alembic upgrade head` before uvicorn, through `backend/entrypoint-api.sh` |
| `PG_SHARED_BUFFERS` | `${PG_SHARED_BUFFERS:-256MB}` (optional) | PostgreSQL shared buffers; not set by default, so `256MB` |

Not set in the file: `JWT_EXPIRA_MIN`, `LOGIN_MAX_FAILURES`, `LOGIN_WINDOW_SECONDS` and the other
defaults of `backend/app/core/config.py`.

**Variable names are a contract with the server.** Never rename or remove a variable that is
already configured on the server (in the Environment Variables tab). A new variable needs a safe
default in the compose, or a notice to the server owner (name, how to generate it, which service)
before the deploy, and this file updated.

## Step by step

1. **Nothing to generate on your machine.** Coolify creates the secrets when the resource is
   created. Do not type your own `POSTGRES_PASSWORD` or `JWT_SECRET`: the file takes the generated
   ones.
2. **Large data: nothing to transfer.** The collector downloads the TSE files itself. The volumes
   fill up during the run (see Expected resources).
3. In Coolify, **New Resource → Docker Compose**: choose the repository and the branch to deploy.
4. **Docker Compose Location**: `/docker-compose.coolify.yml`. Build pack: Docker Compose.
5. **Environment Variables**: nothing to add. Check that the four generated variables from the
   table above are listed. Keep it that way: if a future version of the compose needs a new
   variable, the server owner is told first.
6. **Domains**: set a domain only on the `web` service (the Domains tab of `web`). It replaces the
   generated `SERVICE_FQDN_WEB_80`. No other service gets a domain: `api` is reached through
   `web`'s nginx at `/api/` and `/health`, on the same origin.
7. **Deploy.** Order, enforced by `depends_on` with health checks:
   1. `db` (PostgreSQL 16) and `redis` (Redis 7) become healthy;
   2. `api` runs `alembic upgrade head` (the migrations, every start; they are no-ops when the
      schema is current) and then uvicorn with 2 workers. It becomes healthy when `/health`
      returns 200, after a 30-second start period;
   3. `collector`, `worker-1`, `worker-2` and `web` start.
   Nobody runs migrations by hand.
8. **Check.** Open `https://<your-domain>/health`. The answer must be
   `{"status":"ok","database":"up","redis":"up"}` (HTTP 200). `degraded` with HTTP 503 means the
   database or Redis is down: look at their logs first. Then open `https://<your-domain>/`
   (the dashboard) and `https://<your-domain>/api/docs` (the OpenAPI docs).
9. **Check the logs** in the panel. The lines are JSON objects (one per line). Expected: in `api`,
   the Alembic messages, an `api.starting` line whose `environment` field is `production`, and uvicorn
   listening on port 8000; in `worker-1` and `worker-2`, a `worker.started` line whose `consumers`
   field is `6`; in `collector`, leadership taken by one instance (the other instances, if
   there were any, wait). A `worker.job_failed` (or `worker.queue_read_failed`) line in the workers,
   or a `falha no laço ...` message in the collector, means a TSE file or a step failed; the loop
   keeps running. To follow one request, search its `request_id`: the `x-request-id` response
   header carries the same value.
10. **Create the first account (the administrator).** Registration is open: the first account
    created on an empty database becomes the administrator (`backend/app/modules/accounts/auth/credentials.py`).
    Register it yourself, right after the first deploy, before anyone else reaches the site: the
    sign-up of the dashboard, or `POST /api/v1/auth/register` with your e-mail, name and password. There is no seed and no command-line tool: the data (elections, municipalities,
    polling places) comes from the TSE itself, on the first cycles.
11. **Operate.**
    - Health: `https://<your-domain>/health`; the admin screen shows the collector and worker
      metrics.
    - Logs: in the panel, per container.
    - Backup: only the `pgdata` volume is data that cannot be rebuilt (users, dashboards, alerts,
      events). `brutos` and `fotos` are caches that come back from the TSE.
    - Update: push to the deployed branch and redeploy. Coolify rebuilds the images; `api` applies
      the new migrations on start; `collector` and the workers restart after `api` is healthy.
    - Stop: `SIGTERM` reaches Python through `init: true` (tini); the containers stop within
      10 seconds.

## Expected resources

| Container | Image | Notes |
|---|---|---|
| `db` | `postgres:16-alpine` | `shared_buffers=${PG_SHARED_BUFFERS:-256MB}`, `max_connections=200`, `synchronous_commit=off` |
| `redis` | `redis:7-alpine` | no persistence; `maxmemory 1500mb` with `noeviction` (writes are refused at the cap) |
| `api` | backend image | uvicorn with 2 workers, port 8000 inside the network |
| `collector` | backend image | one leader; the TSE request rate is capped by `TSE_MAX_RPS` |
| `worker-1`, `worker-2` | backend image | 6 consumers each |
| `web` | frontend image (nginx) | port 80; the domain is bound here |

| Volume | Holds | Grows with |
|---|---|---|
| `pgdata` | the PostgreSQL database | the events, the snapshots and the ballot reports stored |
| `brutos` | the raw TSE files (`DIR_BRUTOS=/data/brutos`) | every download of the collector |
| `fotos` | the candidate photo cache | the candidates shown |

Memory and disk are not measured in this repository. The only committed bounds are the ones
above (Redis at 1.5 GB, PostgreSQL shared buffers at 256 MB). After the first full day of the
election, record here the values of `docker stats` and `du -sh` of each volume, so the server
owner can size the next one.

## Differences between the local and the Coolify compose

Local is `docker-compose.yml` (with `docker-compose.dev.yml`, `docker-compose.override.yml` and
`docker-compose.test.yml` on top of it where used); Coolify is `docker-compose.coolify.yml`.

| # | Local (`docker-compose.yml`) | Coolify (`docker-compose.coolify.yml`) | Why |
|---|---|---|---|
| 1 | `ports` on `db` (5432), `api` (8000), `tse-fake` (8089 -> 8080) and `web` (8080 -> 80) | no `ports`; only `web` has a domain | Coolify's proxy routes through the internal network; `ports` would publish PostgreSQL on the host |
| 2 | `web` at `http://localhost:8080` | `web` at the domain generated by Coolify (or yours, in Domains) | one public entry point, same origin for the API |
| 3 | secrets from `.env` (`env_file: [.env]`), database password `eleicoes` | secrets generated by Coolify (`SERVICE_PASSWORD_*`), no `.env` | no development password on a public server |
| 4 | `TSE_AMBIENTE=fake` by default (the mock) | `TSE_AMBIENTE: oficial` | the production data source |
| 5 | `tse-fake` service | no `tse-fake` | the mock is for development only |
| 6 | `migrate` service runs `alembic upgrade head` once | `api` runs it through `backend/entrypoint-api.sh` (`MIGRAR_AO_SUBIR: "true"`), before uvicorn; its `command` is plain uvicorn | one container fewer; nobody has to remember the migration |
| 7 | `worker` with `deploy.replicas: 2` | `worker-1` and `worker-2` as two services | Coolify does not handle replicas well |
| 8 | `redis` with `--appendonly yes` and the `redisdata` volume | no persistence, `--maxmemory 1500mb --maxmemory-policy noeviction` | the Redis data is temporary (queue, metrics, topics); starting empty is faster than replaying a large file |
| 9 | `api` healthcheck without `start_period` | `start_period: 30s` on `api` | the first start runs migrations; without it Coolify marks the deploy as failed |
| 10 | `api` published on the host | `api` reached only through `web` (`/api/`, `/health`) | one domain, no CORS between origins |
| 11 | `COLETAR_ZONAS` from `.env` (default `true`) | `false` fixed | zones multiply the volume |
| 12 | `CORS_ORIGINS` from `.env` (`http://localhost:5173,http://localhost:8080`) | `${SERVICE_URL_WEB}` | the public URL |
| 13 | project named `eleicoes` (`name:` at the top) | no `name:` at the top | Coolify names the project itself |
| 14 | named images (`eleicoes-backend:latest`, `eleicoes-web:latest`) | built by Coolify | the panel tracks the builds |
| 15 | `ENVIRONMENT` not set (`local`) | `ENVIRONMENT: production` | production checks and JSON logs on the server only; see Notes |

Both files keep the same backend image, the same commands for `collector` and the workers, the
same `init: true`, `restart: unless-stopped`, `stop_grace_period: 10s`, the same `db` and `redis`
health checks and the same volume names `pgdata`, `brutos`, `fotos`.

## Notes

- **`ENVIRONMENT=production` is in the file, not in the panel.** It is set in the `x-backend`
  anchor of `docker-compose.coolify.yml`, so every backend service gets it. Nothing to type on the
  server. Effects: the process refuses to start with a missing, short (under 32 bytes) or example
  `JWT_SECRET` (the generated one is 64 characters), and the logs are JSON lines instead of console
  text. The first deploy after this change restarts every backend service with it.
- **`MIGRAR_AO_SUBIR` is in the file, not in the panel.** `backend/entrypoint-api.sh` runs
  `alembic upgrade head` on the `api` container's start because the compose sets it. The other
  backend services do not migrate.
- **`PG_SHARED_BUFFERS` is optional.** It is read by the compose file's `db` service only; if the
  server owner never sets it, the value is `256MB`, as before.
- **Logs are JSON in production, with a request id.** Each API response carries `x-request-id`
  (the caller's value when it is sane, otherwise a generated one). The events and their fields are
  listed in [`docs/system/overview.md`](system/overview.md#logging).
- **The JWS keys of the official TSE are not confirmed** in `backend/app/infra/tse/keys.py`. With
  `TSE_VERIFICAR_JWS=true`, a file whose signature does not match is read as plain `.json`, without
  the verified mark. Watch the `jws_failures` counter (collector metrics, shown in the admin
  screen) after the first collection.
- **The first account is the administrator.** See step 10. Do it before the public announcement.
